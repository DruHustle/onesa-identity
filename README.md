# Onesa Identity

Onesa Identity manages stable account IDs, invitations, approvals, suspension, product grants and the audit trail. Auth0 Universal Login owns credentials, email verification, MFA, recovery and signing keys. Company Portal administrators keep their Portal permissions. Product APIs own resource permissions, tenant memberships and purchase records.

## Run and verify

Requires Node 24, a private writable directory on durable storage, and a confidential OIDC client. Install the locked dependencies with `npm ci --ignore-scripts`. Run `npm test` and `npm run check`. Set the environment in `.env.example` in the deployment secret manager and start `node src/server.js`. HTTP is for the trusted TLS ingress on a private network. The container runs as a non-root user. A persisted encrypted volume, tested backup and independently available hosting are required before piloting with accounts. This implementation serializes policy updates in a single SQLite primary. Multi-instance availability requires a shared strongly consistent store or a tested supported failover configuration; running multiple copies with separate volumes splits the grant history. Audit events are SHA-256 hash-chained and SQLite triggers reject in-place updates/deletes; startup verifies the chain and fails closed on detected drift. This is tamper-evidence, not a signature against a privileged database operator who can rewrite the entire file. Production must periodically anchor the verified audit head in a separate immutable system and retain tested encrypted backups.

## Oracle deployment

Build the existing Dockerfile from the approved commit on Oracle. Set `IDENTITY_IMAGE` to that exact local image and reserve a free loopback port for `IDENTITY_HOST_PORT`. Use one service instance and one private, durable `IDENTITY_VOLUME` containing the commissioned `identity.sqlite` and its WAL files. The container runs as UID 1000; the database directory must be writable by that user. Restore a consistent backup or perform the reviewed Portal import before cutover. The production service refuses to create an empty authority. If the mounted database disappears or its file is replaced while running, readiness and policy decisions return HTTP 503; restart against the verified store after recovery.

Set `IDENTITY_ORIGIN` to the browser’s actual HTTPS account origin and register **exactly** `IDENTITY_ORIGIN/callback` on the dedicated Auth0 Account client. Provide its `OIDC_CLIENT_ID`, the reviewed `RESOURCE_CLIENTS_JSON` registry, and optionally the database connection name used for password recovery. Mount the Account client secret via `OIDC_CLIENT_SECRET_PATH` and the shared Action policy credential via `ACTION_POLICY_KEY_PATH`. File-backed Compose secrets are host binds. Keep their parent directory private and grant read permission only to the container user and the operator. The Auth0 issuer is fixed at `https://auth.onesa.eu/`. The Account client and shared policy credential are separate from each product’s client secret.

Use `docker compose --env-file /etc/onesa/identity/production.env -f deploy/compose.oracle.yaml up -d --wait` to launch. Check `/readyz` on the reserved loopback port before connecting the existing TLS ingress. Route the account application’s own GET and POST paths, including `/account/access`, `/account/enrollment`, `/account/recovery`, `/admin/change` and `/admin/invite`, to this service. Keep Auth0 authorization, token, discovery, provider callbacks and hosted login pages with Auth0. The Compose definition publishes only to loopback; it does not modify DNS, route the custom domain or enable Auth0 Actions.

## Tenant and routing

Account sign-out always removes the local session. Set `AUTH0_LOGOUT_ENABLED=true` after the dedicated Auth0 Account application allows the exact `IDENTITY_ORIGIN` as a logout return URL. With this setting the browser continues to Auth0 and returns to Account after ending its SSO session.

**Production host separation:** When `auth.onesa.eu` is the DNS-only CNAME for the Auth0 custom domain, leave it pointing to Auth0. Do **not** route `/register`, `/callback` or `/internal/decision` at that hostname unless a separately security-reviewed edge configuration supports the split. Host Onesa Account at `https://account.onesa.eu` with its own TLS ingress to the Oracle Identity service, set `IDENTITY_ORIGIN=https://account.onesa.eu`, and retain `OIDC_ISSUER=https://auth.onesa.eu/`. The built-in production registration return registry supports both Account origins. The dedicated Auth0 confidential application must allow **exactly** `https://account.onesa.eu/callback` for the Account callback, use `https://account.onesa.eu/account/registration/resume` for Application Login URI, and use `https://account.onesa.eu` for any configured logout and web origins. The post-login and step-up Actions must use `POLICY_ORIGIN=https://account.onesa.eu` and `POLICY_URL=https://account.onesa.eu/internal/decision`. Keep production secrets in the Oracle host and the Auth0 Action secret store, never in source control. Only switch each product registration link from the existing route after `/readyz`, `/register`, email verification, account return and both user/admin approvals have passed on the new host. Do not replace the existing Portal registration route during this verification.

Use separate tenant, grant database, keys, clients, sender and operator access for staging and production. Configure `auth.onesa.eu` as the provider custom domain and verify DNS/TLS. Host the administration application on a separate service. The browser-visible origin that starts OIDC must equal `IDENTITY_ORIGIN`: the `__Host-` flow cookie, callback URI, CSRF Origin check and internal policy URL all bind to that same origin. Therefore, a branded `https://auth.onesa.eu/admin` deployment must route **all Identity-owned paths** (`/admin`, `/account`, `/register`, `/login`, `/callback`, `/logout`, `/step-up`, `/verify-factor`, and `/internal/decision`) to the Identity application, with `IDENTITY_ORIGIN=https://auth.onesa.eu`, the Auth0 Action `POLICY_ORIGIN=https://auth.onesa.eu`, and `POLICY_URL=https://auth.onesa.eu/internal/decision`. Keep Auth0 discovery, authorize, token, JWKS and other provider-owned paths with Auth0. Routing only `/admin` to an app whose `IDENTITY_ORIGIN` is a different host will break the host-only flow cookie and callback; do not qualify that arrangement. If the selected Auth0/custom-domain/edge setup cannot safely split these paths, publish the independent administration origin directly in Portal until the branded route is verified. Do not send IdP session cookies to an unrelated upstream.

Register the confidential account application with the **exact** `IDENTITY_ORIGIN/callback`, Code with PKCE, RS256 and public registration only on approved connections. Do not set a tenant-wide default API audience on the account application. The account UI supports `/account`, `/register`, `/login`, `/admin`, and provider-driven MFA and database-connection recovery. Enable the tenant's actual email delivery, verification, password recovery, enrollment and recovery factors. Qualification must cover delivery in a controlled inbox, existing MFA enrollment, recovery to the intended screen and link handling across browser/device configurations. The UI produces one-time invite links bound to an address and expiry; operators deliver these to the intended recipient. Privileged sign-in requires MFA in the last five minutes. The account status and role checks run again on every admin request.

Onesa Account owns registration for all products. Link to the configured Account origin at `/register?audience=user` or `/register?audience=admin`. The existing `/register` entry selects user registration. Both start one confidential Auth0 Code + PKCE transaction. Identity keeps the requested tier and any valid invitation in its one-use server-side flow. It obtains the email and stable provider subject from the verified callback. The signed-in account page supports requesting the other tier on the same account.

When registration starts in a product, send `product` and `platform` as well as the registration tier. For example, `/register?audience=admin&product=farmer&platform=ios` returns to the installed Farmer app. Platforms are `web`, `ios`, and `android`; web is the default. The eight product IDs are `ai`, `drone`, `robot`, `farmer`, `factory`, `logistics`, `mobile`, and `pasofi`. Portal and Internal Documents use `portal` and `internal-documents` on web.

Identity's confidential callback remains `/callback`. After verified enrollment Identity redirects directly to the registered product landing or native app link. The URL carries no Identity code, token, contact address or requested document path. The product keeps the intended screen in its own browser or app state and resumes its own registered OIDC flow. A return to the product confirms the handoff. New account access and staff actions still depend on the applicable approvals.

The exact production landing URLs are listed in `src/registration-returns.js` for Account origin `https://auth.onesa.eu`. Other deployments set `REGISTRATION_RETURNS_JSON` to their reviewed registry. Setting it replaces the full default registry. Each product maps platforms to a fixed URL or to `{"user":"…","admin":"…"}` for tier-specific endpoints. The registry accepts HTTPS or an installed app's registered scheme for that product on mobile. Configure links to product-owned registration completion routes separately from OIDC callback allowlists. The incoming request supplies only product/platform/tier identifiers.

Connect the Account client's [Auth0 application login URI](https://auth0.com/docs/authenticate/login/auth0-universal-login/configure-default-login-routes) to `IDENTITY_ORIGIN/account/registration/resume` for the verification-email return. A 24-hour, host-only browser receipt lets Identity restart the correct flow after verification or an expired OIDC transaction. With two unfinished products in the same browser, the page asks which product to continue. A valid callback always uses its own transaction's product. A different browser without that receipt returns to Onesa Account. Route this endpoint to the Account service together with the normal enrollment paths.

Register the confidential Account client on the approved database or passwordless connection. Bind `auth0/pre-registration.cjs` to its Pre User Registration flow with the dedicated `ACCOUNT_CLIENT_ID`. The Action accepts interactive hosted registration only for that client. Products provide central registration links and use their own OIDC clients for sign-in. External enterprise or social identity providers manage their own credentials. A provider credential alone confers no Onesa product access.

Activate the account and review its shared registration from `/admin` with a different Identity administrator and fresh MFA. A verified registration by itself grants no product roles. One approved **user** registration enables entry to Smart Farmer, Smart Factory, Smart Logistics and AI Platform as `user`, Drone and Robot as `viewer`, and Onesa Mobile and PasoFi as `customer`. An approved **administrator** registration uses the canonical `administrator` product role where the audience has completed the role rollout, and `administrator` for Company Portal. For Farmer, Logistics, and Factory, set `"sharedAdminRole": "administrator"` in each audience’s resource registry only after its managed backend accepts that role with recent MFA. The older `"admin"` registry value is temporarily accepted during migration; Identity does not emit it as a role. Until an audience is enabled, shared administrator registration receives only its ordinary user entry there. For new Portal staff a signed `https://onesa.eu/claims/portal_staff_registration` boolean is emitted only for an inherited Portal administrator role after fresh MFA. Explicit Portal grants do not receive this enrollment marker.

Each product can open a product-scoped administrator list at `/admin?product=<product-id>`. Product admin pages should link there with their own fixed product ID. A product administrator can add or remove administrators only for that product. Identity accepts only active accounts with an existing verified provider link, requires recent MFA for every change, and records the actor, target, product, role and result in the append-only audit journal. Removing an administrator preserves their existing ordinary product grant. The central Identity administrator can still manage any product and review the full audit history.

An explicit per-product assignment, including a pending, rejected or revoked row, takes precedence over a shared role. Identity governance and Internal Documents continue to require explicit access. Each service enforces tenant, farm, site, resource and purchase permissions. Existing verified accounts retain their UUID and provider subject. An existing account may request either tier from its account page; existing approvals and product-scoped administrator grants continue to apply. New shared scope requires independent review. Changing account status to suspended or rejected blocks subsequent issuance. Shared approvals, removals and denials are recorded in the hash-chained journal and survive authenticated Identity recovery. Repeated registration never reactivates a removed tier. A legacy Portal rollback records shared registration dispositions for operator review because its schema cannot express the central tiers.

Register one API identifier per product, with token lifetime at most 300 seconds and explicit web/native clients (no wildcard callbacks). Native applications use the system browser, public clients and S256. For example, configure the Docs API audience `https://api.docs.onesa.eu` with product `internal-documents` and the Farmer API audience `https://api.farmer.onesa.eu` with product `farmer`. Register the internal Docs client with its exact callback on `docs.internal.onesa.eu`. `docs.onesa.eu` is the public Developer Docs site and does not participate in sign-in. An existing engineering membership can issue only the legacy `engineering-documents` scope. The internal edition must restrict that scope to Engineering and apply each record’s ACL. Any explicit `internal-documents` assignment, including revocation, takes precedence. Only the internal edition has an OAuth client. The logical Docs API audience does not route requests. Populate `RESOURCE_CLIENTS_JSON` with an object keyed by audience; each value has its product ID and the array of provider-issued client IDs. Register Portal under `https://api.portal.onesa.eu` and product `portal` if confirmed for that environment.

Bind `auth0/step-up.cjs` and then `auth0/post-login.cjs` in the dedicated tenant. Configure the same policy endpoint and credential in both Actions. For an interactive login without an MFA ACR the first Action asks policy whether the approved role requires MFA, then challenges enrolled factors or starts enrollment. The second Action rechecks current authorization and the completed factor. Put `POLICY_ORIGIN` (the exact canonical HTTPS origin configured as `IDENTITY_ORIGIN`), `POLICY_URL` (exactly `POLICY_ORIGIN` plus `/internal/decision`), and `POLICY_KEY` (the same high-entropy value as the server's `ACTION_POLICY_KEY`) into the Action secret store. The Action refuses to send its bearer key if the URL origin differs, even when the path is correct. The service rechecks live approval and resource grants before token issuance or refresh. Without the control plane, provider issuance fails closed. The signed claims under `https://onesa.eu/claims/` are `user_id` (Onesa UUID), `products` (one current product), `roles` (roles for that product) and optional `mfa_time` (provider-recorded Unix seconds). APIs must verify issuer, expected audience, RS256 signature, expiry, and product access against an independently retained trusted JWKS before resource ACL checks. Require actual recent MFA for sensitive actions. Block on unknown keys during outages. An existing access token can authorize within its original lifetime, absent a stronger product-local rejection; revocation is checked again on next issue. Product sessions must not silently extend that window.

Use New Universal Login and enable **Customize MFA Factors using Actions** under **Security → Multi-factor Auth → Additional Settings**. Enable the tenant-approved factors before binding the Actions. The first Action can enroll users during ordinary interactive MFA in OTP, WebAuthn, Guardian push or phone when enabled by the tenant. It can challenge existing supported enrollments and offer enabled recovery codes or email. An operation requires a pre-existing enrollment beyond implicit email. Refresh and noninteractive grants never start an enrollment or challenge. Auth0 documents how the [sequenced MFA methods](https://auth0.com/docs/actions/reference/post-login/post-login-api-object) pause execution before the next Action.

Ordinary Portal login requests the standard PAPE multi-factor ACR and receives the provider-recorded `mfa_time`. For a sensitive operation, Portal starts a new OIDC authorization code flow with S256, a one-use state and nonce, both that ACR and `urn:onesa:authentication:operation-mfa`, `prompt=login`, and `max_age=0`. The first Action stores the original nonce and timing in Auth0 transaction metadata before the challenge. The policy Action releases `https://onesa.eu/claims/operation_mfa_nonce` only in the approved Portal access token after observing a new completed factor. Portal must verify the signed access and ID tokens, compare the operation nonce, compare the MFA timestamp with its transaction start, and match both provider subject and stable Onesa UUID to the initiating session. Consume the proof once for that exact session and operation. Qualify both the baseline and operation paths with an enrolled pilot account before enabling the managed Portal route.

## Migration and rollback

1. Freeze source policy writes briefly or arrange an independently verified change capture and a final export before switching their owner. Use `psql -XqAt -v ON_ERROR_STOP=1 -f migration/export-portal.sql` with a read-only role against the source to export one consistent snapshot. Store the output in protected custody. It contains contact records, approval evidence and review notes and must remain private. The read-only SQL selects named fields and excludes credentials and secrets. Production credentials, MFA seeds, password hashes and customer attachments stay in the source systems.
2. Independently verify proof of both the legacy UUID and the provider issuer/subject, or use a verified provider migration receipt. Build a protected manifest containing `id`, `issuer`, `subject`, `method` (dual-authentication or provider-import-receipt), and `receipt` for each verified link. These tools consume trusted operator inputs and cannot establish the validity of an external receipt. A matching email is insufficient. Blank proof inventory means no provider links. Password/MFA credential migration and reenrollment must be qualified with the chosen tenant before cutover.
3. Before import, resolve any duplicate legacy email contacts (including case or whitespace variants) with the account owners; never merge identities on email evidence alone. The importer rejects malformed addresses and ambiguous contact ownership atomically, and normalizes accepted contacts. Run `node migration/reconcile.js apply DATABASE SNAPSHOT_KEY SNAPSHOT.json PROOFS.json HTTPS_ISSUER` against an isolated database. Replaying the same export leaves subsequent account changes intact. A changed export under the same key or a conflict aborts atomically. Review all unresolved records before pilot. The importer retains explicit product decisions, legacy Docs membership IDs, pending registrations and Drone tenant inventory. Legacy implicit global privileges and email-only or unlinked Docs memberships require separate owner disposition. Preserve local resource ACLs and legacy IDs in each product. Tenant records, document ownership and purchases remain in their original product stores. An import alone does not establish continuity of those product records.
4. Resolve later ownership receipts with `node migration/link-proof.js DATABASE HTTPS_ISSUER PROOFS.json`. Bootstrap exactly one independently authorized Identity administrator using `OIDC_ISSUER=https://auth.example/ node migration/identity-admin.js DATABASE STABLE_USER_ID APPROVAL_RECEIPT`. The bootstrap verifies that the account has an independently evidenced link for that exact configured issuer, and a stale grant on a suspended account does not block replacement. Legacy Portal owner does not confer Identity administration. Verify MFA from the administrator's browser. Retain a consistent baseline backup with the fingerprint/watermark and test restores on an isolated host.
5. During rollback, freeze writes, export `node migration/reconcile.js delta DATABASE SNAPSHOT_KEY DELTA.json`, restore the baseline separately, then run `node migration/reconcile.js replay RESTORED_DB SNAPSHOT_KEY DELTA.json`. Replays verify the baseline, journal sequence and changed IDs. Conflicts stop the restore. New accounts, bindings, suspensions and entitlements survive the replay. The recovery target uses the same Identity schema. Compare product-owned records against the original snapshot before reopening writes. Unused invitation URLs, pending login exchanges and sessions should be invalidated/reissued on failover. To revert to the legacy issuer, a separate legacy-side import of these reconciled changes, credential continuity and product readback are required. Reverting DNS alone can revive revoked rights.
6. Qualify Portal, Internal Documents and Farmer with separate test roles first. Measure grant and removal latency through the deployed API, during provider outage with keys available before and after restart, and after expiry. Verify role isolation and real existing records on all deployed web and native clients before expanding. Product services, RADIUS, voucher issuance and device telemetry remain independently authorized.

## Verification scope

The synthetic tests exercise the administration and policy routes, stale forms, role boundaries, duplicate email ownership, grants and revocation, suspension, one-use browser challenges, OIDC Code/PKCE/nonce and signed token verification, Action failure, bulk-import replay and restore after cutover updates. A hosted tenant, DNS, production data, controlled-inbox delivery, device and native-client tests require separate release evidence.
